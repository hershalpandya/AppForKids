# Worksheet-to-game adoption plan

**Status: planning for review; no workflow or schema changes are implemented.** This plan addresses [#26](https://github.com/hershalpandya/AppForKids/issues/26), part of [#22](https://github.com/hershalpandya/AppForKids/issues/22). It connects the [shared visual proposal](proposed-visual-direction.md) and [classification proposal](game-classification-proposal.md) to the existing private authoring and parent review workflow. Those sources own the decisions; this plan does not approve their remaining proposals or authorize implementation.

## Decision boundary

The family chose **Petits Pas**, a brighter, more colorful direction, an all-games catalogue with optional year, subject and topic filters, multiple topics per game, and **À classer** for unknown legacy games. P1 and P3 remain supported. The palette, illustrations, preview label, subject/topic labels, single-subject contract, filter details, schema transition and versioned legacy mapping still need review. The example classifications below are candidates, not approved curriculum labels. Consult the linked sources for their full decision and owner lists; do not invent values or force a worksheet into an unrelated topic to complete a draft.

Today, the [worksheet skill](../.agents/skills/worksheet-to-game/SKILL.md) and [P1](p1-worksheet-preview.md) and [P3](p3-worksheet-preview.md) guides describe schema version 1, a year-first preview, and no subject/topic fields. The current parser and release validator accept v1, and the release validator rejects unexpected fields. The preview is a separate app using the shared parser and round rules, not an approval or release. Until the coordinated implementation lands, continue using those current instructions and do not add proposed fields to a v1 definition or claim that classification filters or new styling already exist.

## Intended authoring flow after agreement and implementation

1. **Read and preserve the source.** Redact names, school identifiers and unrelated handwriting before sharing. Keep scans, transcriptions, source review, uncertainties, answer keys and game drafts in the parent's private folder outside the checkout. Read every page, record page/item references, set doubtful items aside and ask the parent about missing or conflicting information. Check the intended year and learning goal against the worksheet and the relevant Fédération Wallonie-Bruxelles reference.
2. **Consult the shared sources.** Before composing or revising a draft, read the current [visual source](proposed-visual-direction.md) and its agreed resource/component guidance, then the current [classification vocabulary and compatibility plan](game-classification-proposal.md). Use the agreed shared resources in the preview and family app; game JSON remains learning content, not a second theme. Review actual text, symbols and layout against the shared guidance without hiding tasks or implying answers. Proposed token examples and preview labels are not approved values.
3. **Choose and review classification.** Confirm the worksheet's P1 or P3 year and select the agreed subject and all applicable topics from the bundled vocabulary; discuss uncertain or missing terms with the parent and vocabulary owner rather than guessing. Candidate examples are P1 counting → `mathematics` / `counting` and P3 synonyms → `french` / `synonyms`. Multiple topics are a family choice; the proposed one-subject, unique nonempty topic list, stable IDs and validation rules await agreement. Show the resolved French labels and year to the parent with the draft. Record proposed new vocabulary for review, not as an unvalidated local invention. Use the supported definition schema only after runtime, preview and release validation support it together.
4. **Compose and correct.** Use the matching or tap-to-choose interaction that fits the worksheet. Keep only game content in the definition and maintain a separate answer key for the exact revision, including displayed prompts, choices or tiles, solutions, correct feedback and retry hints. A correction retains the game ID, increments the revision, preserves previous private files and updates the source review and key. Recheck the changed content and classification, then give the parent the review, key, preview title and outstanding questions.
5. **Preview and seek parent review.** Load the private draft in the separate preview app, check its persistent, legible preview identity, locate the draft in the all-games catalogue and inspect its year and resolved subject/topics. When the chosen filters are implemented, exercise the relevant year, subject and each topic and confirm the game appears once; clear filters and recover from no matches. A same-ID draft replaces the bundled entry in preview and its own classification should be shown. Play the complete draft against its answer key, including wrong answers, hints, correct feedback, completion, replay and return. For corrections, inspect each changed item and reopen the verified draft at its instructions screen. The parent reviews both the learning content and classification; preview does not imply approval.
6. **Approve and release separately.** After the parent reviews the exact revision, use the existing private approval and signed-release process, selecting explicit `id@revision` snapshots. Keep approval receipts and snapshots private and unchanged. A definition change requires a new revision and review/approval; packaging must preserve selected bytes and use the appropriate supported schema rules. Review classification changes for old approvals and settle a versioned mapping before claiming they are stable. Retain the existing higher-version-code recovery path and offline update checks.

## Representative checks for implementation

These are future observable checks at the agreed installed-app and worksheet-preview seams, not results of this planning ticket. Use synthetic fixtures for automated checks and screenshots; never commit private worksheets, answer keys or child data. Record the fixture and revision, build, device/Android version, date, reviewer, outcome and follow-up owner. Run the existing preview and APK smoke checks where relevant; physical tablet review complements, rather than is replaced by, emulator checks.

| Draft | Content and interaction review | Design and classification review |
| --- | --- | --- |
| P1 tap-to-choose, e.g. [synthetic counters](../tests/fixtures/les-jetons-a-reunir.json) | Compare each prompt, visual row, choices, solution and feedback with its exact answer key; try wrong and correct choices, hint, completion and replay. Verify each correction in a new revision. | Confirm P1 and the reviewed subject/topics are visible and filterable after implementation; check countable objects, readable instructions, large separate targets and feedback in words as well as visual cues. |
| P3 matching, e.g. [synthetic corrected synonyms](../tests/fixtures/les-mots-de-meme-sens-corrige.json) | Compare the worked example and each pair with the exact key; try an incorrect match and hint, retry, complete and return. Verify changed hints after a correction. | Confirm P3 and reviewed subject/topics, including each applicable topic; check readable French word tiles, two clear columns, selection and matched states, and non-color feedback. |

For both, inspect preview identity, shared component states, wrapping at normal and enlarged text, contrast, focus and accessible names, and target spacing on the family tablet using the visual source's review criteria. Check all-games visibility, applicable filters and clearing them, no-match recovery, and offline play. For a same-ID replacement, confirm the draft's revision, content and classification are the ones shown. Keep screenshots free of private material. Record family review and unresolved findings; do not represent proposed styling or a successful emulator run as physical approval.

## Compatibility and delivery

- **Existing v1 drafts:** continue to preview and validate under current rules. Future support must read them without rewriting their content; use the agreed compatibility mapping for known starters and **À classer** for unknown legacy games. The latter must remain visible in the all-games catalogue. Proposed year filtering and exclusion from subject/topic filters await agreement.
- **Approved releases:** do not edit snapshots, receipts or starter assets in place. The future parser, preview and release validator need coordinated support for old and new schemas, a bundled vocabulary, and a reviewed, versioned mapping that cannot silently change the classification of an already reviewed release. Verify an old approval alongside a new one, compare packaged bytes, play offline after a signed in-place update, and recover with an earlier approval using a higher version code. Mapping storage and review semantics remain open.
- **Guidance to update after decisions and implementation:** revise the worksheet skill and P1/P3 guides together for consulting the shared design source, vocabulary selection and uncertainty, supported schema, preview identity and catalogue/filter review. Update [parent handoff](parent-handoff.md), release guidance and wiki links for exact-revision review, compatibility and recovery. Preserve the existing private-file, correction and parent approval instructions. Replace current year-first directions only when the new journey actually ships.
- **Sequence:** maintainer and family agree visual details and classification/vocabulary; maintainer resolves schema and mapping with preview/release owners; implement parser, validator and compatibility together; implement catalogue and shared presentation, then authoring and preview guidance; exercise both representative drafts and release compatibility before rollout. Split this into independently reviewable implementation issues only after the outstanding choices are resolved; this document does not implement them.
